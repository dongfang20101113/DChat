# 群文件加密：设计与取舍

> 目标：**所有房间都可以选择开启**。开启后，该房间的文件在服务端落盘时是密文。
>
> 这篇是设计稿，先定方案再写代码。里面每个"不这么做"都写了原因——加密功能的
> 坑几乎全在取舍上，不在算法上。

## 一、先划清边界：加密防的是谁

这一点必须先说清楚，否则容易做成"看起来很安全、实际没用"。

| 威胁 | 这个功能能不能防 |
|---|---|
| 服务器磁盘被拿走（备份、快照、云厂商运维） | ✅ **能**——落盘是密文，没有密钥解不开 |
| 服务器进程被拿下（有人登录机器） | ❌ **不能**——密钥在那个进程的内存里，一起被拿走 |
| 群主/管理员偷看群文件 | ⚠️ 看设计：如果密钥由成员各自持有，管理员也解不开；如果服务器发密钥，就能 |
| 网络传输被监听 | ❌ 不需要——传输本来就有 ECDH + AES-256-GCM |

**结论：这是"静态数据加密"（encryption at rest），不是"端到端加密"。**
把它说成 E2E 是不诚实的，界面上也不能这么写。

## 二、密钥从哪来、谁能拿到

这是整个设计的核心。三个候选：

| 方案 | 密钥存在哪 | 好处 | 坏处 |
|---|---|---|---|
| A. 服务器生成并保管，验证成员身份后下发 | 服务端 `dchat-files/<房间>/key.bin` | 实现最简单，成员变化即时生效 | **服务器能解密**——防不住"进程被拿下"，也和"群主偷看"半斤八两 |
| B. 群主生成，服务端只存密文，成员通过私聊传密钥 | 服务端只存密文 | 真正的端到端 | 换机/重装就丢密钥；管理员踢人后**旧成员仍能解旧文件**；新成员看不到历史文件 |
| C. 折中：服务器保管密钥，但**退出即吊销** | 服务端 | 权限模型和现有 `RMEMBERS` 一致，行为可预期 | 仍然是静态加密 |

**选 C。** 理由：

1. 这个项目现在的权限模型是**服务端权威**（谁能下载文件由服务端校验成员身份）。选 B 会让"踢人"变成一个无法保证的承诺——被踢的人手里还留着密钥，你却告诉群主"已经踢掉了"。**宁可能力小一点，也不要做假承诺。**
2. B 还有一个绕不开的问题：**新成员看不到历史文件**。群文件的价值很大一部分在历史里，这个损失太大。
3. C 的"服务器能解密"这个缺点，和现在的实际情况是**同一件事**——服务器本来就能读到所有群聊内容。加密在这里的价值是**防磁盘泄露**，不是防服务器。

界面上会写清楚：**"开加密后，文件在服务器上是密文（防止磁盘/备份泄露）；服务器进程本身仍可解密。"** 不能让人以为这是 E2E。

## 三、具体怎么做

### 3.1 密钥

- 每个房间一把 **AES-256 密钥**，32 字节，`std::random_device` 生成。
- 存 `dchat-files/<房间ID>/room.key`，**权限 0600**（和 `dchat-admin-token.txt` 同级待遇）。
- 服务端启动时读入内存（`g_roomKeys`），关闭时不清（内存清不清意义不大）。

### 3.2 落盘格式

```
DCHATENC1 <16 字节随机 IV> <密文>
```

- 头部魔数 `DCHATENC1` 让"这个文件加密了没有"**可判定**——迁移、排错时不用猜。
- 每个文件**独立随机 IV**（GCM 下 IV 重用是灾难性的，绝对不能用一个全局计数器）。
- 复用现有 `crypto_backend_openssl.cpp` 的 AES-256-GCM，不引新依赖。
- 只加密文件内容；文件名、大小、属主这些元数据留在服务端存储结构里（它们本来就在）。

### 3.3 开关（每房间独立）

- 新设置项 `fileencryption`，走现有的 `GSET` / `RSET` 通道，和 `cachemaxmb`、`joinmode` 一样。
- **只有群主/管理员能改**（落在"管理两栏"的那一栏里）。
- 广播给成员，三端显示一个"🔒"标记。

### 3.4 开关的边界（这里最容易糊弄过去，必须写死规则）

改成"开"之后：

- **新上传的文件**：加密落盘。
- **已经存在的明文文件**：**不回溯加密**。往回加密要对每个文件解密再加密、中途失败会留下半个损坏文件，风险大于收益。界面上明确提示"该群目前有 N 个文件是加密前的明文"。
- 改成"关"之后：新文件明文；**已加密的文件保持密文**（能解，但不再加密新的）。

### 3.5 谁能解密

权限完全复用现有的下载校验：**服务器确认你是该房间成员后才发文件**。

- 成员：服务端解密后经已有的加密通道发给你（和现在的下载路径一样）。
- **退出/被踢**：立刻失去资格——下一次请求就下载不到。这就是选 C 的好处。
- 下载路径要不要变？**不变。** 服务端内部解密，客户端拿到的是明文流，**老客户端完全不受影响**——这是"保证老客户端读取不受影响"的落点。

## 四、老客户端兼容（明确写死）

| 场景 | 行为 |
|---|---|
| 老客户端（不声明 `rooms1`） | 完全不知道有加密这回事；上传的文件按房间当前开关处理，下载照常——**零影响** |
| 老客户端上传到已开加密的房间 | 服务端照样加密落盘（客户端无感） |
| 老客户端下载已加密的文件 | 服务端内部解密后下发，客户端无感 |
| 新客户端 | 多显示一个 🔒 标记，别的没变 |

**关键：加密/解密完全发生在服务端内部，协议一行不改。** 这是能做到"老客户端零影响"的唯一办法，也让这个功能的风险大幅下降。

## 五、风险清单（实现时要盯的）

1. **IV 重用**：每个文件独立随机 IV。用计数器/固定值就是灾难。要有测试。
2. **密钥文件权限**：`0600`，和口令文件同级。忘了就是白做。
3. **半写文件**：加密写失败要删掉临时文件，不能留下"看着有其实解不开"的文件。
4. **回退开关**：`fileencryption` 改回 false 后，已加密文件仍必须能读——读路径只看文件头的魔数，**不看房间当前开关**。
5. **磁盘统计**：加密后文件会大 16+32 字节左右，`maxservertemp` 的统计要按**落盘后的字节数**算，否则预算会算漏。

## 六、实现顺序（下一步）

1. `src/file_crypto.h/.cpp` + 单测（加解密往返、IV 不重用、魔数判定、错密钥必须失败）
2. 服务端：密钥文件读写、`fileencryption` 设置项、上传/下载路径接上
3. 三端：显示 🔒（桌面端群设置、安卓、CLI `/set fileencryption`）
4. `docs/rooms-protocol.md` 补 `fileencryption` 一行
5. 协议 e2e 加一节：开加密 → 传 → 关 → 还能读 → 明文文件不受影响
