# 断联、切房残留、历史重复：根因与修法

这一轮修的是用户实际用出来的问题。每条都写了**根因**——里面有两处是"看起来像网络问题，
其实是代码 bug"。

## ① 切换聊天房后还能看到上个房间的消息 / 历史越切越长

**根因**：服务端每次收到 `ROOM <id>` 都会把该房间历史重放一遍（`RHIST`），
而三个客户端的处理都是**纯追加**。于是切一次多一份历史、多一条「以上是历史消息」。
用户截图里出现**两个**「以上是历史消息」就是直接证据。

**修法**：**按序号去重**。`RHIST` 自带单调递增的 `seq`：

| 端 | 位置 |
| --- | --- |
| 网页版 / Linux CLI | `client_core/chat_core.cpp`（`lastHistorySeq_`） |
| Win32 桌面端 | `src/client.cpp`（`Session::lastHistorySeq`） |
| Android | `ui/ChatState.kt`（`lastHistorySeq: Map<String, Long>`） |

序号 <= 已显示过的就跳过。**不去改协议**——`seq` 本来就在 `RHIST` 里。

网页版额外做了一步：切房时网关发 `CLEAR` 让浏览器清屏，并调
`ChatCore::ForgetDisplayedHistory()` 忘掉该房间的历史位置——**两件事必须一起做**，
只清屏不遗忘的话，重放的历史会被去重逻辑吞掉，页面变成一片空白。

桌面端和 Android 不调 `ForgetDisplayedHistory`：它们保留自己的滚动记录，
靠去重来避免重复，切回去还能看到之前的上下文。

## ② 网页版"自动断联" —— 是我自己写的 bug

**根因**：网关给浏览器连接设了 **30 秒接收超时**（`SetReceiveTimeout(handle, 30000)`），
而接收循环里 `got <= 0` 一律 `break`。等于**30 秒没有输入就主动断开浏览器**。

**修法**：超时不算断开。

```cpp
if (got == 0) break;              // 对端真的关了
if (got < 0)  continue;           // 超时：继续等，只数次数
// 连续 120 次（30s × 120 = 1 小时）完全没有数据才判死连接
```

**公网实测**（部署后，用不存在的账号避免污染生产）：

```
连接: Open
空闲 40 秒  -> ✓ 保持连接  状态=Open
再发命令    -> 收到回复，状态仍 Open
```

顺带补了**双向保活**：网关每 25 秒给浏览器发一个 WebSocket `ping`，浏览器自动回 `pong`。
中间设备（家用路由器、运营商 NAT）看到双向流量就不会把连接当空闲回收。

## ③ 网页版自动重连 + 自动登录

- 断线后按 **2s → 4s → 8s … 最多 30s** 退避重连（以前断了只能手动刷新页面）
- 勾「记住账号，下次自动登录」后，打开页面直接连
- 凭据存在该浏览器的 `localStorage` 里，**密码是明文**——页面文案已写明，公共电脑别勾

桌面端和 Android 的自动登录**还没做**。

## ④ 桌面端本来就有心跳

`src/client.cpp` 里已经有每 45 秒一次的 `PING`（服务端回 `PONG`，客户端不把它显示成提示）。
所以桌面端的"断联"不是保活问题——**是断了之后不会自动重连**，这块还没做。
