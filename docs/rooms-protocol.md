# dchat 多会话协议（私聊 / 群聊）

这份文档是**服务端、Windows 桌面端、Android 端共同遵守的唯一契约**。
改协议必须同时改这里和三个端；协议不同步不会在编译期暴露，只会表现为运行时的
「消息莫名其妙不见了」或「加群没反应」。

---

## 一、总览

### 1.1 房间（会话）三态

dchat 以前只有一个全局房间。现在统一抽象成 **Room**，三种 `kind`：

| kind | 含义 | 成员关系 | 能否删除 | 能否退出 |
| --- | --- | --- | --- | --- |
| `hall` | 大厅。ID 固定 `hall`，全服唯一 | 登录即自动成为成员 | 否 | 否 |
| `group` | 群聊。ID 由建群者自填，建后不可改 | 申请 / 审核加入 | 群主可解散 | 可以 |
| `dm` | 私聊。ID 由服务端分配（`dm-000001`） | 由服务端建立，固定两人 | 否 | 否（只能删本地记录） |

大厅**在数据结构上就是一个群聊**（有成员表、群公告、群文件、管理员），
唯一的区别是上面那三条硬规则。聊天室里"最大的房间"指的就是它。

### 1.2 房间 ID 规则

- 群 ID：**3–16 个字符**，只允许 `[a-z0-9_-]`，输入统一转小写，建后**不可更改**。
- 保留名：`hall`，以及 `dm-` 前缀。用户不能建这两个。
- 私聊 ID：`dm-` + 6 位十进制序号，服务端分配，客户端只负责回传，**不要自己构造**。

为什么强制小写：ID 不可改，如果允许大小写，`MyGroup` 和 `mygroup` 就是两个群 ——
用户搜不到自己刚建的群，多复制一个大写字母就永远进不去，而且没有补救机会。
界面在提交前会**显示规范化后的 ID 让用户确认**，不做静默改名。

### 1.3 与老客户端的兼容（硬约束）

线上服务器还有正在使用的旧版桌面端与安卓端，因此：

1. **老客户端不发 `HELLO`**，服务端就一直走明文、并且**不进房间模式**。
2. 房间模式由 `HELLO` 的第 4 个字段声明（见 2.1）。没声明 = 老客户端 =
   服务端只维护大厅、只发 `SAY`、行为与本功能上线前**逐字节一致**。
3. 大厅的消息**永远**用老格式 `SAY <时间> <昵称> <文本>`；非大厅用新的 `RMSG`。
   新客户端把 `SAY` 归属到 `hall`，不需要服务端额外标注。

### 1.4 消息路由模型

| 场景 | 行为 |
| --- | --- |
| 会话列表 | 登录后服务端主动下发 `ROOMLIST`（含大厅） |
| 实时消息 | 服务端把该用户**所有房间**的新消息都推给他（带房间 ID），客户端自行分发 |
| 历史 | 客户端切到某会话时发 `ROOM <id>`，服务端回该房间最近若干条 `RHIST` |
| 离线补发 | **第一版不做**按房间的离线补发。重新登录后切到该会话即可拉到最近历史 |

「当前会话」只用来决定 `MSG` 发到哪个房间，默认是 `hall`（老客户端行为不变）。

## 二、C → S 命令

### 2.1 握手与能力声明

```
HELLO <版本> <公钥B64> <随机数B64> [<能力列表>]
```

第 4 个字段是逗号分隔的能力标签，可省略（老客户端就没有）。

| 标签 | 含义 |
| --- | --- |
| `rooms1` | 客户端支持本文档描述的全部多会话命令 |

也可以登录之后再声明一次：

```
C -> S  FEATURES <能力列表>
S -> C  FEATURES <能力列表>      服务端确认（只回它自己也支持的那些）
```

为什么除了 `HELLO` 还要有这么一条：`HELLO` 是**加密握手**，把能力声明绑死在那里，
等于"不支持加密的客户端永远用不了群聊"，而且任何针对多会话的自动化测试都得先
实现一遍 ECDH 才能开口说话。这条命令让能力声明和加密彻底解耦。

安全上不用担心：`roomsCapable` 只决定服务端**多发**哪些消息给这个连接，
每一个群操作本身都会另外校验成员身份和角色，谎报能力换不到任何权限。

服务端确认后**立刻补发一次会话列表**（如果已经登录）。客户端**必须**以收到的
`FEATURES` 为准：没有 `rooms1` 就退回"只有大厅"的老界面（连的是旧版服务端时会发生）。

### 2.2 会话

```
ROOM <房间ID>          切换当前会话并拉取最近历史
ROOMS                  请求会话列表
DM <昵称>              打开（不存在则创建）与某人的私聊
```

### 2.3 群管理

```
GCREATE <房间ID> <群名B64>                 建群。ID 不合法 / 已存在 -> ERROR
GSEARCH <关键词B64>                        搜索向公众展示的群
GJOIN <房间ID>                             申请 / 加入
GLEAVE <房间ID>                            退出群聊
GSET <房间ID> <设置名> <值>                 修改群设置（群主或管理员）
GMEMBER <房间ID> <昵称> <角色>              设 / 撤管理员（仅群主）
GNICK <房间ID> <昵称> <群昵称B64>           改群昵称（自己改自己；管理员可改别人）
GKICK <房间ID> <昵称>                      踢人（群主或管理员）
GREQS <房间ID>                             查看待审的入群申请
GREQ <房间ID> <昵称> <ok|no>               审核入群（群主或管理员）
GDELETE <房间ID>                           解散群聊（**仅群主**）
```

`GSEARCH` 的关键词、`GCREATE` 的群名、`GSET` 的 `name` / `announcement`、
`GNICK` 的群昵称都用 **Base64**（可能含空格）；其余参数是明文。

**设置名（`GSET` 的第二个参数）与取值范围：**

| 设置名 | 含义 | 值 |
| --- | --- | --- |
| `name` | 群聊名称 | 1–24 个码点 |
| `maxmembers` | 最大人数 | 2–2000，且不得小于当前成员数 |
| `joinmode` | 加群方式 | `direct` / `approval` / `auto` |
| `listed` | 向公众展示 | `true` / `false` |
| `cachemaxmb` | 总缓存最大大小（MB） | 1–65536 |
| `announcement` | 群公告 | 最多 500 个码点，可为空 |
| `importantnotice` | 消息重要提醒 | `true` / `false` |

加群方式的三个值**不是同义的**：

- `direct`（直接添加）：申请即入群，服务端不拦。
- `approval`（管理员审核）：进待审队列，必须管理员点同意。
- `auto`（自动审核）：进待审队列后**立刻自动放行**，但服务端会给管理员发一条通知。
  如果它和 `direct` 表现完全一样，管理员就永远不知道有谁进来过，这个选项也就没有意义。

### 2.4 私聊与黑名单

```
BLOCK <昵称>           拉黑
UNBLOCK <昵称>         解除拉黑
BLOCKS                 列出黑名单
```

黑名单由**服务端**持久化并拦截，否则拦不住对方发消息。拦截范围：
私聊消息双向拦截（他发给你的你收不到；你发给他的也发不出去，提示已拉黑）。
大厅和群聊的公开消息**不拦** —— 那是公共空间，拦了会让群聊看起来缺了一块。

### 2.5 消息与文件

```
MSG <文本>             在「当前会话」发言（老命令，保持兼容）
```

文件沿用现有命令不变（`FILE_SEND` / `FILE_CHUNK` / `FILE_END` / `FILE_CANCEL` /
`FILE_GET` / `FILE_THUMB` / `FILE_THUMB_GET`），作用域同样是「当前会话」。
服务端为每个文件记录它属于哪个房间，下载时校验下载者是不是该房间成员。

### 2.6 重要提醒（@）

`@全体成员` 由服务端强制校验：

- 只有该群的**群主或管理员**能发，普通成员发 -> `ERROR`，不入历史、不广播。
- 群设置 `importantnotice = false` 时，谁都发不了。
- 其余 `@某人` 由客户端本地解析（和现在一样），服务端不参与。

这样做的理由：`@全体成员` 是唯一能越过所有人免打扰设置的东西，把它做成纯客户端
约定等于没约束 —— 任何客户端都能发。

## 三、S → C 命令

### 3.1 会话信息

```
RINFO <房间ID> <kind> <显示名B64> <群主> <成员数> <最大人数> <我的角色> <加群方式> <listed>
```

紧跟在后面的永远是 7 行 `RSET`（见 3.2），把该房间全部设置项报一遍。
把设置从 `RINFO` 里拆出去，是为了以后加设置项时不用改 `RINFO` 的字段数 ——
字段数一变，三个端一起解析错位。

- `显示名B64`：群是群名，私聊是**对方昵称**（省得每个客户端各算一遍）。
- `我的角色`：`owner` / `admin` / `member`。
- 大厅没有群主，该字段为空字符串。

```
RSET <房间ID> <设置名> <值>              单个设置项
RMEMBERS <房间ID> <昵称> <角色> <群昵称B64>   一行一个成员
RMEMBERS_END <房间ID>                    成员列表结束
RHIST <房间ID> <序号> <原始协议行>         历史回放，一行一条
RHIST_END <房间ID>                       历史结束
```

> `RSET` 里 `name` 和 `announcement` 的值是 **Base64**（可能含空格），其余是明文。
> 设置名是固定集合，客户端不会猜错。

### 3.2 会话列表

```
ROOMLIST <房间ID> <kind> <显示名B64> <成员数> <最大人数> <我的角色>
ROOMLIST_END
```

### 3.3 消息

```
SAY <时间> <昵称> <文本>                  大厅消息（老格式，兼容老客户端）
RMSG <时间> <房间ID> <昵称> <文本>        非大厅消息（群聊 / 私聊）
REVENT <时间> <房间ID> <文本>             房间内事件：加入、退出、被踢、设置变更、审核结果
```

> ⚠️ **时间戳在前**。这不是随手定的：服务端所有带时间的行都走同一个 `Timed()`
> 辅助函数，它把时间拼在最前面（`SAY` / `SYS` / `JOINED` / `FILE_OFFER` 全是这样）。
> 新命令要插队把房间号放前面，就得为它们单独写一套拼装逻辑 —— 而两套拼装逻辑
> 迟早会有一套写错，且只在特定命令上表现出来。所以 `RMSG` / `REVENT` / `GREQ` /
> `RFILE_OFFER` 一律**沿用"时间在前、房间号紧随其后"**。

群昵称的显示：`SAY` / `RMSG` / `REVENT` 里的 `<昵称>` 一律发**账号名**，
客户端按自己缓存的成员表把群昵称换上去显示。服务端不做替换，因为同一个账号在
不同群里群昵称不同，服务端替换会让历史记录回放时显示错人。

### 3.3.1 文件（附件）

大厅**完全沿用原来的命令**，一个字段都没动：

```
FILE_OFFER <时间> <昵称> <文件ID> <文件名B64> <字节数> <有无缩略图> [<种类>]
```

非大厅的房间多带一个房间号，并且**换成另一个命令名**：

```
RFILE_OFFER <时间> <房间ID> <昵称> <文件ID> <文件名B64> <字节数> <有无缩略图> [<种类>]
```

为什么另起一个命令名而不是给 `FILE_OFFER` 加字段：老客户端按**位置**解析
`FILE_OFFER`，第 6 格是"有无缩略图"。往中间插房间号会让它们把房间号当成缩略图
标志、把缩略图标志当成种类。换成新命令名，老客户端会当未知命令丢掉 ——
而它们本来也不在群里，丢掉是正确的。

上传与下载的命令（`FILE_SEND` / `FILE_CHUNK` / `FILE_END` / `FILE_CANCEL` /
`FILE_GET` / `FILE_THUMB` / `FILE_THUMB_GET`）**都不变**，作用域是「当前会话」。
服务端为每个文件记录它属于哪个房间：

- 上传时房间号在 `FILE_SEND` 那一刻**钉死**，之后切会话不影响这次上传
  （否则文件前半段会进 A 群、后半段进 B 群，而 `.part` 文件只有一个）。
- 下载时校验请求者是不是该房间成员。**这一步不能省**：文件 ID 是全局递增的
  （`F1`、`F2`…），不校验的话，任何登录用户猜几个 ID 就能把别人的私聊附件拉走。

### 3.4 群管理回执

```
GHIT <房间ID> <群名B64> <成员数> <最大人数> <加群方式>    搜索结果，一行一个
GHIT_END
GREQ <时间> <房间ID> <昵称>                              有人申请入群（通知管理员）
GREQ_END <房间ID>                                        申请列表结束
GDMLINK <房间ID> <对方昵称>                              私聊已建立
GBLOCKS <昵称>                                           黑名单列表，一行一个
GBLOCKS_END
```

`GREQ` 的两种出现场景：`GREQS` 的回应（逐行列出待审的人）和主动通知管理员。
两者字段一致，客户端当成同一件事处理即可。

## 四、权限矩阵（管理员可设 vs 成员本地）

用户明确要求区分这两类，代码里也用两个结构体物理隔开：
服务端代码一行都不会引用 `RoomPrefs`。

### 4.1 群管理员可设（存服务端，广播全群）

| 项 | 群主 | 管理员 | 普通成员 |
| --- | --- | --- | --- |
| 群聊名称 / 群公告 | ✅ | ✅ | ❌ |
| 最大人数 / 加群方式 / 向公众展示 / 总缓存最大大小 / 消息重要提醒 | ✅ | ✅ | ❌ |
| 审核入群、踢人、查看申请 | ✅ | ✅ | ❌ |
| 设 / 撤管理员（`GMEMBER`） | ✅ | ❌ | ❌ |
| 改别人的群昵称 | ✅ | ✅ | ❌ |
| 改**自己**的群昵称 | ✅ | ✅ | ✅ |
| 转让群主 / 解散群聊 | ✅ | ❌ | ❌ |

### 4.2 成员本地设置（只在各自客户端，**永不上传**）

| 项 | 说明 | 默认值 |
| --- | --- | --- |
| 免打扰 | 新消息不提示、不闪任务栏、不计未读 | **大厅默认开**，其余默认关 |
| 置顶 | 会话列表排最前 | 关 |
| 重要提醒仍然提醒 | 免打扰时，`@我` / `@全体成员` 是否照常提示 | 开 |
| 本地缓存上限 | 本机保存的该会话聊天记录 + 缓存文件上限 | 128 MB |

私聊/群聊一视同仁，都是这四个。私聊额外有**黑名单**，但黑名单要服务端拦，见 2.4。

### 4.3 群主退出群聊

群主退群时自动转让：优先给**最早加入的管理员**，没有管理员就给最早加入的其他成员。
群里只剩群主一人时**不允许退出** —— 没人可接，退掉会留下一个没有群主的孤儿群。

## 五、服务端存储布局

| 路径 | 内容 |
| --- | --- |
| `dchat-rooms.txt` | 房间元数据（群 + 私聊）。大厅不写，由代码建 |
| `dchat-history.txt` | **大厅**的历史。沿用原文件名，升级不丢历史 |
| `dchat-history-<房间ID>.txt` | 其他房间的历史。ID 已限定 `[a-z0-9_-]`，可直接当文件名 |
| `dchat-files/` | **大厅**的文件暂存目录。沿用原路径 |
| `dchat-files/<房间ID>/` | 其他房间的文件暂存目录 |
| `dchat-blocks.txt` | 每用户的黑名单 |

`dchat-rooms.txt` 的格式（制表符分隔，三种记录）：

```
R <id> <kind> <群名B64> <群主> <最大人数> <加群方式> <listed> <缓存MB> <重要提醒> <公告B64>
M <id> <昵称> <角色> <群昵称B64>
P <id> <昵称>
```

### 真机测试发现并已修复的问题（2026-10-10）

这三条**全是自动化测试和离屏渲染盖不到的**，只有真人点界面才发现：

1. **消息完全不显示**（严重）。服务端日志收到 `MSG a: 1`，但两个客户端界面一条都没有。
   根因：`AppendToSession` 不管是不是当前会话，一律往 `session.items` 塞；而界面读的是
   `g_items`（当前会话的活副本）。更糟的是 `SwitchSession` 会用 `g_items` **覆盖**
   `old.items`，那些消息彻底消失。
   **不变量**：`g_items` = 当前会话的活副本；`session.items` 只对**非当前**会话有效。
   投递必须按 `index == g_currentSession` 分流。
2. **表头的「搜索 / 新建」按钮算得到、点得到，但从来没画**。代码看起来完整（有矩形、
   有命中测试、有点击回调），屏幕上什么都没有。用户反馈原话："没有你说的加号"。
3. **「向公众展示」点了不变**。点击只发 `GSET`，本地什么都不做；就算服务器的 `RSET`
   回来了，设置窗口也不会重画。改成**乐观更新**：点完立刻改本地镜像并重画，
   `RSET` 回来再确认（开关 / 加群方式 / 文本编辑三条路径共用 `ApplyLocalRoomSetting`）。
4. **群聊窗口的输入框是系统默认白底黑字**，压在深色界面上很突兀。
   加 `WM_CTLCOLOREDIT` + `fieldBrush` 跟随主题。
